# Description

The infrastructure includes three services, each running in its own dedicated container:
- **NGINX**, a web server whose role is to receive HTTP/HTTPS requests from browsers and process them.
In this project, it serves as the sole entry point for the infrastructure. All connections therefore pass through it via port 443 using HTTPS.
It directly serves static files (images, CSS, JS) and delegates PHP code to php-fpm via the FastCGI protocol.

- **WordPress + php-fpm**, a CMS (Content Management System), a system that allows you to create and manage a website without coding.
This CMS is written in PHP. That is why we will also use php-fpm (FastCGI Process Manager), which is a PHP process manager that executes the WordPress code.
Both run together in the same container: Php-fpm receives PHP files from nginx, executes them, and returns the generated HTML.

- **MariaDB**, a relational database management system (an open-source alternative to MySQL). WordPress uses it to store all its data: posts, users, settings, and comments.
Without a database, WordPress cannot function because it has nowhere to store the information.

Each service is built from a custom Dockerfile, a configuration file, and an entrypoint script.

# Instructions

For this project, you need to set up a virtual machine running Alpine or Debian Linux. Install Docker, Docker Compose, and make on it, as Alpine does not include them by default. Clone the repository into the VM.

You must manually configure the secrets and .env file so that they are not included in the repository for security reasons.
Services can be launched from the project root: `make` to build and start all containers, `make down` to stop these containers, and `make fclean` to delete everything and start from scratch.

You also need to make a configuration change to access your site:
Add 127.0.0.1 [login.42.fr](http://login.42.fr) to /etc/hosts, so you can open https://login.42.fr in the browser (since this will be a self-signed certificate, you’ll need to accept the self-signed certificate warning).

# Project description


### Virtual Machines vs. Docker:
Both are technologies that isolate an environment, though each does so at a different level.

A virtual machine simulates physical hardware, a complete computer, and runs on a hypervisor (such as VirtualBox, VMware, etc.). 
It includes its own full OS kernel, its own drivers, and the entire operating system. It therefore consumes a lot of memory and can take some time to start up.
Docker (or containers) virtualizes at the OS level. Containers share the host machine’s kernel and include only the libraries and dependencies necessary for the application being virtualized. It is lighter than a VM, so it starts up faster.

For Inception, we create a VM in which we clone our repository into the root directory and launch Docker, which runs three services: the NGINX web server, the MariaDB database, and the WordPress application. This is a project that requires simulating and learning how to manage the two layers of isolation.


### Secrets vs. environment variables:
When using Docker, a secret refers to any data (passwords, SSH keys, API keys, TLS certificates, etc.) that should not be transmitted over a network or stored in plain text in a Dockerfile or in the source code.
With Docker Compose, services can add the 'secret' attribute, allowing secrets to be used without having to convert them into environment variables.
These secrets are stored (in a text file) in the /run/secrets/ directory inside the container (and are mounted as read-only and as tmpfs (RAM), not on the container's disk), they never appear in Docker logs. Docker mounts it into the container at a specific path: /run/secrets/secret_name. And the container reads the file.

To store any other data (non-sensitive or semi-sensitive) that needs to be easily accessible between services, users can use environment variables in a .env file, ensuring that no private data is visible in this file. The .env file, unlike secrets, provides variables to docker-compose.yml itself, not directly to the containers.


### Docker Network vs. Host Network:
The NGINX, WordPress, and MariaDB containers need to communicate with each other, that’s what the network is for.
With Docker Network, a bridge network uses a software bridge that allows containers connected to the same bridge network to communicate with each other, while ensuring they remain isolated from containers not connected to that bridge network. 
As a result: Containers on one network cannot see those on another network, and containers cannot see the ports of your host machine unless you specify them with a ‘ports:’ directive. This provides better security than with host network.

With host network, the container directly shares the host machine’s network. There is no longer any network isolation. The container therefore uses the machine’s ports as if it were a normally installed application.


### Docker Volumes vs. Bind Mounts
Volumes are persistent storage spaces implemented by the container engine, which can be configured and reused by multiple services.
A Docker volume is an independent filesystem fully managed by the Docker daemon, which exists as a standard file or directory on the host.
It allows containers to use data located outside their own container, for example, for backups—or to share data between containers. The container may die or be recreated: the data survives. 
There are three main types of Docker volumes:
	- Bind mounts map a host directory or file to the container and are useful for transferring configuration files or source code between the host and the container.
	- Named volumes are created and managed by Docker, providing a convenient way to store and share data between containers.
	- Anonymous volumes are created automatically, as they are not assigned a name.

# Design choices

Alpine Linux is a distribution specifically designed for containers; it is minimalist and security-focused. Alpine has fewer packages installed than Debian, for example, so there are fewer potential security vulnerabilities, which helps ensure compliance with the security best practices required for this type of project. The project also prohibits the use of pre-built service images, Alpine allows to build them yourself by installing only what is strictly necessary.
The 3.22 version of alpine was used, it is the penultimate version as requested by the subject. Choosing the penultimate version “guarantees” stability, a lightweight system, and security, fewer packages mean fewer vulnerabilities.

Since MariaDB and WordPress require initial setup on first startup (create the database, configure users, etc.), I use entrypoint scripts rather than a simple CMD command : this is what is needed for initial setup on first startup (create the database, install WordPress) before launching the main service.

In a standard Linux system, process 1 is init (or systemd). It has a special role: it adopts orphaned processes and handles signals (SIGTERM, SIGKILL, etc.). When you run 'docker stop', Docker sends a SIGTERM to the container’s PID 1.
In a Docker container, the main process becomes PID 1.
For example with NGINX, if you start the service via a shell script, PID 1 is the shell, not nginx. When Docker sends a SIGTERM to shut down the container gracefully, the shell receives it but does not necessarily pass it on to nginx. Result: nginx is abruptly killed.
Thus, to ensure that the main process receives system signals and allows containers to shut down properly, I use exec, which replaces the shell process with nginx. Nginx immediately becomes PID 1 and receives signals correctly.
